# Роадмап виправлення безпеки та надійності

Статус: **критичні виправлення реалізовано; Rules розгорнуті в staging, Functions перевірені лише локально через Emulator Suite (без billing)**  
Оновлено: 2026-07-25  
Джерело: статичний аудит коду застосунку.

## Мета

Закрити можливість несанкціонованого доступу до профілів і сесій, прибрати втрату даних під час синхронізації та зробити запуск профілів передбачуваним. Роботи виконуються в наведеному порядку: наступна фаза не повинна починатися до прийняття критеріїв готовності попередньої.

## Порядок робіт

| Фаза | Пріоритет | Результат | Залежності |
| --- | --- | --- | --- |
| 0. Архітектурне рішення | P0 | Затверджена модель доступу та сховища секретів | — |
| 1. Негайне стримування ризику | P0 | Закрито витік усіх профілів/cookies | Фаза 0 |
| 2. Авторизація та секрети | P0 | Немає SHA-256-паролів у Firestore і дефолтного admin/admin | Фаза 1 |
| 3. Синхронізація профілів | P1 | Немає зайвих записів і silent data loss | Фаза 1 |
| 4. Надійність запуску | P1 | Діагностика, проксі, lease і fingerprint поводяться стабільно | Фаза 3 |
| 5. Якість та релізний контур | P2 | Тести, журналювання й захищена поставка | Фази 1–4 |

## Фаза 0 — зафіксувати цільову архітектуру

- [x] Визначити: cookies є синхронізованими секретами, локально шифруються через `safeStorage`, а cloud-sync виконується тільки через callable endpoint.
- [x] Визначити єдине джерело прав доступу: серверний ACL `authorizedUsers`, а не UI-клієнт.
- [x] Обрати серверний довірений контур для адміністративних дій: Firebase Callable Functions із Firebase Admin SDK; поки що запускається локально в Emulator Suite, без хмарного billing.
- [x] Затвердити модель конфліктів: server-side lease для запуску плюс revision/optimistic concurrency для синхронізації.
- [ ] Сформувати план міграції наявних `profiles`, `teamUsers` і локальних файлів без втрати активних сесій.
- [ ] Визначити політику відкликання доступу для offline-пристроїв і строк дії локального кешу.

**Критерій готовності:** є коротка ADR/схема даних із відповідальним, датою міграції та способом rollback.

## Фаза 1 — негайно закрити несанкціонований доступ (P0)

- [x] Змінити Firestore Rules: `profiles` не можна `list/get/create/update` лише за фактом `isAuthorized()`.
- [x] Прив’язати доступ до конкретного профілю до серверного ACL; `allowedProfiles` перевіряється у Rules і Cloud Functions.
- [x] Заборонити неадміністраторам довільно змінювати `url`, `proxy`, `activeHolder`, `lastSyncUser`, `lastSyncDevice` та cookies.
- [x] Винести session-cookies у довірений callable endpoint із перевіркою ACL та чинного lease.
- [x] Обмежити поля, розмір документа та типи даних у Rules; заборонити невідомі поля.
- [x] Додати Firebase Emulator-тести для: користувача без доступу, користувача з доступом, адміністратора, підміни ID та прямого SDK-виклику.
- [x] Запустити Emulator-тести локально на JDK 25: ACL, заборона list/прямого SDK-write працівнику та allowlist полів профілю пройдені. CI запускає цей же набір на JDK 21.
- [x] Розгорнути Rules окремим контрольованим релізом і перевірити їх на staging-проєкті Firebase (`accbrowser-staging-20260725`, Firestore `eur3`).
- [ ] Розгорнути Cloud Functions у staging після свідомого рішення підключити billing: Firebase вимагає Cloud Build та Artifact Registry. До цього застосунок не повинен використовувати cloud-виклики Functions у реальних даних.

**Критерій готовності:** непривілейований авторизований користувач не може через Firebase SDK отримати, змінити або видалити чужий профіль чи його cookies.

## Фаза 2 — авторизація, паролі й локальні секрети (P0)

- [x] Прибрати `passwordHash` із `teamUsers` та будь-якої синхронізації між пристроями; є сумісна міграція для cloud-admin.
- [x] Перестати похідно генерувати Firebase-пароль із локального SHA-256-хешу: Firebase secret тепер виводиться з введеного пароля, а локальний verifier є окремим.
- [x] Перенести створення, reset, видалення Firebase Auth-користувачів у серверний Admin SDK для керування командними акаунтами.
- [x] Для локальної fallback-авторизації використовувати versioned `scrypt` з унікальною сіллю; старий SHA-256 verifier мігрується при першому успішному вході.
- [x] Прибрати автоматичне створення `admin/admin`; перший адміністратор задає пароль під час одноразового локального bootstrap.
- [x] Виправити міграцію старих паролів: перевірка дефолтного значення відбувається до видалення поля.
- [x] Валідовувати пароль у main-process: 12–256 символів, заборона порожнього/дефолтного значення.
- [ ] Зберігати локальні ключі/токени у системному keychain (Keychain/Credential Manager), а не в plain JSON.
- [x] Шифрувати локальні cookies профілів через Electron `safeStorage` (системний keychain) на підтримуваних ОС; за недоступного ключа зашифрований файл не перезаписується порожніми даними.
- [ ] Запустити примусову зміну/скидання чинних паролів і відкликати старі облікові матеріали.

**Критерій готовності:** у Firestore немає хешів паролів; жоден новий інсталяційний сценарій не дає доступ через відомі дефолтні облікові дані.

## Фаза 3 — безпечна й економна синхронізація (P1)

- [x] Не надсилати session-запис, якщо cookies не змінилися; використовується повний SHA-256 fingerprint cookies.
- [x] Змінити 5-секундний polling на debounce після фактичної зміни cookies плюс фінальний flush при штатному закритті застосунку.
- [x] Хешувати повний значущий стан cookie, а не лише `name/value/domain/path`.
- [x] Ввести `revision`, `updatedBy` і optimistic concurrency/transaction: сесійні server-side записи та admin-збереження відхиляють застарілу ревізію з явним конфліктом.
- [x] Не обрізати cookies мовчки: надвеликий payload лишається локально, cloud-sync відхиляється з явним повідомленням користувачу.
- [ ] Розділити метадані профілю й сесійний стан у різні документи/канали синхронізації.
- [x] Не завантажувати всю колекцію профілів для працівника: клієнт запитує лише явно дозволені ID.
- [x] Додати локальні агреговані метрики за 30 днів: writes/profile/day, bytes synced, конфлікти, cloud-помилки й listener errors; cookies та інші секрети не журналюються.

**Критерій готовності:** незмінний профіль не генерує періодичних cloud writes; паралельні зміни або конфліктують явно, або детерміновано зливаються без втрати сесії.

## Фаза 4 — запуск браузера, діагностика та володіння профілем (P1)

- [x] Реалізувати `PreflightChecker.checkUrlAccessibility()`.
- [x] Зробити реальний network-check проксі перед запуском, з timeout і зрозумілою помилкою.
- [x] Використати один URL/parser для проксі у preflight і launcher; підтримуються HTTP(S), SOCKS, IPv6 та percent-encoded credentials.
- [x] Не встановлювати `activeHolder` до успішного `puppeteer.launch`.
- [x] Замінити `activeHolder` на server-side lease: транзакційне захоплення, TTL, heartbeat і звільнення; звичайне metadata-збереження не може перезаписати lease зі stale локальної копії.
- [x] Зафіксувати fingerprint на рівні профілю; перше захоплення профілю атомарно встановлює його через callable endpoint, наступні пристрої використовують той самий набір.
- [x] Забезпечити узгодженість fingerprint, OS, Chrome version, locale, timezone та user-agent; одна функція застосовує ідентичність профілю до стартової і кожної нової вкладки. Для нового fingerprint спершу береться фактична major-версія Chrome, а за відсутності її в dataset застосовується підтримуваний fallback із журналюванням.
- [x] Прибрати URL-based logout blocker: запити більше не перехоплюються й не блокуються приховано; відстеження cookies для нових вкладок збережено.
- [x] Валідувати URL профілю, timezone, user-agent, формат і максимальний розмір cookies у main-process; backup-імпорт має межі розміру та кількості профілів.

**Критерій готовності:** невірний проксі не запускає Chrome; збій запуску не залишає stale lock; повторний запуск одного профілю має стабільний fingerprint.

## Фаза 5 — спостережуваність, тести й релізи (P2)

- [x] Замінити знайдені порожні `catch` на структуровані повідомлення з контекстом без cookies, паролів і proxy secrets; новий device ID більше не містить ім’я користувача ОС.
- [ ] Показувати користувачу помилки, що потребують дії; технічні деталі — лише в захищеному журналі.
- [x] Показувати помилку session-sync у renderer: локальна сесія лишається збереженою, а користувач отримує одноразове повідомлення про конфлікт або cloud-відмову.
- [x] Додати unit smoke-тести для `AuthManager`, `SyncManager`, parser-а проксі та валідації IPC (`npm test`).
- [x] Додати інтеграційні Firebase Emulator-тести: Rules ACL та callable Functions для team-user provisioning, lease, revision-conflict і session sync; обидва набори успішно запущені локально.
- [x] Додати ізольований режим запуску застосунку через Firebase Emulator Suite: `npm run start:emulators` з'єднується лише з `127.0.0.1` і не потребує billing.
- [ ] Додати lint і повний build-тест у CI.
- [x] Додати GitHub Actions security gate: чисте встановлення без lifecycle scripts, `npm run verify`, Rules- та Functions-Emulator тести, syntax-check і `git diff --check`.
- [x] Оновити production-залежності та перевірити lockfile: `npm ci --dry-run` проходить, `npm audit --omit=dev` не знаходить уразливостей. High-ризики залишаються лише у dev-ланцюжку `electron-builder` і потребують окремої перевірки build-оновлення.
- [ ] Окремо оновити Functions dependencies з major-міграцією та повним Emulator regression: поточний `npm audit --prefix functions --omit=dev` знаходить 9 moderate у транзитивному ланцюжку `firebase-admin`/`uuid`; запропоноване виправлення потребує major-upgrade `firebase-admin`.
- [x] Увімкнути CSP для renderer і явно заборонити непотрібну навігацію/створення вікон Electron.
- [ ] Підписувати й notarize macOS-збірки; підписувати Windows-збірки; переглянути необхідність `asar: false`.
- [ ] Підготувати incident runbook: компрометація cookies, відкликання користувача, rollback Rules, ротація ключів.

**Критерій готовності:** критичні сценарії мають автоматичні тести, а реліз не може бути зібраний при падінні перевірок безпеки.

## Контрольний чекліст релізу

- [x] Firestore Rules перевірені Emulator-тестами та розгорнуті у staging.
- [ ] Відсутні `passwordHash` у cloud-документах і логах.
- [ ] Усі чинні сесії/паролі, що могли бути скомпрометовані, відкликані або ротовані.
- [ ] Cloud writes незмінного профілю виміряні й не мають періодичного росту.
- [ ] Перевірені одночасне редагування і запуск профілю з двох пристроїв.
- [ ] Перевірені HTTP/SOCKS/IPv6-проксі та зрозуміле повідомлення про їх недоступність.
- [ ] Всі main-process IPC handlers валідовують вхідні дані й права доступу.
- [ ] CI пройшов, пакети підписані, є план rollback.

## Власники та контроль

Для кожної позначки перед початком виконання треба додати відповідального, посилання на задачу, дату, ризик міграції та критерій перевірки. P0-завдання не варто випускати частково: зміни Rules, backend-авторизації та міграція даних мають бути узгодженим релізом.
